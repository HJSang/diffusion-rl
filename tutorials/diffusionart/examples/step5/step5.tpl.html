Reading and running the DiffusionART code

After this step you can trace one DiffusionART iteration through the real repository from YAML to optimizer step, map every tensor in the core kernels to the paper's symbols, run the CPU smoke test and a paper recipe, and set up fair experiments against the baselines that live in the same framework.

Why read the implementation at all

Steps 1 to 4 gave you the algorithm as three equations: a covariance guidance $G(c)$, a frozen target $v_{\text{tgt}} = v_\theta^{(0)} + G(c)$ on visited ODE states, and two disjoint MSE updates with a trust-region mask. The paper's Algorithm 1 fits in eight lines. The repository that produced the paper's numbers is roughly 17,000 lines of Python. Most of that code is not the algorithm. It is model adapters, reward wrappers, asset preparation, distributed bookkeeping, checkpointing and evaluation, and it encodes dozens of decisions that the paper does not mention: a sign convention, an $\varepsilon$ floor, an unbiased estimator, a gradient clip, a loss denominator that ignores microbatching, a rule for prompts whose $K$ rewards are all equal.

Those decisions matter when you reproduce a curve, compare against a baseline, or port the method into your own stack. This chapter is a guided tour. We start from a map, trace one iteration of the CPU smoke test with real printed tensors, read the three core files line by line, and finish with commands for real GPU runs, a debugging plan, intuition-building experiments and porting notes for a Megatron + SGLang style framework.

From LLM RL

The shape of the code will feel familiar: a rollout phase that produces a cache, a scoring phase, an advantage-like statistic computed per prompt group, and a training phase with a fixed number of optimizer steps per rollout. The differences are in what the cache holds (continuous latent tensors and velocities, not token ids and logprobs), what the "advantage" is (a direction in latent space shared by all states of a prompt, not a scalar per sample), and what the loss is (a regression, not a ratio objective).

Repository map

The repository installs as the package visual-diffusion-rl with one console script, visual-rl, that points to visual_rl.train:main. Everything under src/visual_rl/ splits into four layers: pure kernels with no model knowledge, model-independent training plumbing, backends that own a concrete model family, and the supporting cast (models, rewards, evaluation, assets).

The split between algorithms/ and training/ is the most useful thing to internalize. A kernel like art_loss never sees a model, an optimizer or a rank. It receives a batch of current predictions and frozen tensors and returns a per-item loss vector of shape [N]. The caller owns the denominator, the microbatching and the optimizer boundary. This is the same separation a good LLM RL framework draws between "compute per-token loss" and "reduce and step".

One iteration of the CPU smoke test, traced

The fastest way into the code is the tensor fixture, backends/tensor_fixture.py. It replaces the diffusion transformer with a two-layer MLP over a 4-dimensional "latent" (input: state, $t$, a scalar prompt condition), and replaces the reward model with $R(x_0,c) = -\tfrac14\lVert x_0 - c\mathbf 1\rVert^2$. Everything else (rollout cache, covariance, objective, accumulation, checkpointing, status file) is the production code path. Read it top to bottom as a worked example.

  • Schedule. $t \in \{1, 0.75, 0.5, 0.25, 0\}$. The fixture trains on the first three states (selected = (0, 1, 2)); the last interval is not trained.
  • Cache. states and old_velocities have shape [N, S, D] = [8, 3, 4]: 8 trajectories, 3 cached states each, 4 latent dimensions. There are no log-probabilities (None): an ODE rollout has no transition density, and ART does not need one.
  • Rewards and guidance. Prompt 0 has rewards with mean $-1.917$ and spread (mean absolute deviation) $0.964$; prompt 1 is much tighter (MAD $0.230$). Its raw covariance has RMS $0.051$, 29 times smaller than prompt 0's $1.47$. After normalization both prompts get a guidance direction of unit RMS and magnitude $1.0$. This is the paper's claim in numbers: the guidance scale does not depend on the reward scale or spread.
  • Windows. Each window holds 12 items, one per (trajectory, cached timestep) pair: 4 trajectories × 3 timesteps. Window 2 starts at trajectory 4, so in this fixture window 1 is all of prompt 0 and window 2 is all of prompt 1. We come back to this split later.
  • Update 1 loss is exactly the mean of $t$. At update 1 the parameters equal $\theta_{\text{old}}$, so $v_\theta = v_\theta^{(0)}$ on every cached state and the residual is exactly $G(c)$, whose MSE is $\operatorname{rms}(G)^2 = 1$. The loss is the $t$-weighted mean: $\tfrac13(1 + 0.75 + 0.5) = 0.75$. This identity is a free sanity check on any real run (see the GPU section).
  • Update 2. The first update moved the shared MLP, so on window 2's states the drift $d$ is nonzero. The KL proxy reaches $1.41\times10^{-5}$, above $\delta=10^{-5}$, and 1 of 12 items is masked. The loss fell to $0.708$ because the displacement $d$ already points partly along $G$, so $\lVert G-d\rVert^2 < \lVert G\rVert^2$ on most items.

How the rollout works

The sampler and the cache

collect_rollout in training/rollout.py is the single rollout function used by ART and, with stochastic steps enabled, by the GRPO family. For ART every step is deterministic Euler. The model is called once per step per microbatch, the transition is applied, and if the step index is one of the selected training timesteps, the input state, the predicted velocity, the next state and the transition mean are copied to CPU in fp32.

Variable to paper mapping: noise is $x_1 = \epsilon$; state at loop index $i$ is $x_{t_i}$, with t = sigmas[index] $=t_i$; velocity is the cached rollout prediction, the paper's $v_\theta^{(0)}(s_t)$ up to sign (next callout); states[row, slot] is the visited state $s_t$; endpoints is $x_0^{(i)}$. Microbatching here is purely physical: inputs and innovations are fixed before the loop, so the cache does not depend on sampling.microbatch.

Pitfall: the code's velocity has the opposite sign

The repo follows diffusers/SD3: the network predicts $\tilde v = \epsilon - x_0$, and flow_transition integrates with mean = x + dt * v where dt = sigma_next - sigma is negative. Writing $h = t - t_{\text{next}} > 0$, the code's step is $x_{t-h} = x_t - h\tilde v$. The paper's step is $x_{t-h} = x_t + h v$ with $v = x_0 - \epsilon$. So everywhere in the code $\tilde v = -v$, dt $= -h$, the cached old_velocities are $-v_\theta^{(0)}$, and a code target old - G is the paper's $v_\theta^{(0)} + G$. Keep this one substitution in mind and every sign in art.py lines up with the paper.

What is reused, and what it costs in memory

ART's efficiency claim (README, "Reuse rollout predictions") is that training re-uses the rollout states and their old predictions. NFT, by contrast, re-noises each endpoint to fresh states and needs an extra no-grad forward of the old policy on those new states. In ART the only model calls per iteration are the rollout forwards (no grad) and one forward plus backward of the current policy per trained (trajectory, timestep) item.

The price is CPU memory. The cache holds four tensors of shape $[N_{\text{rank}}, S, \text{latent}]$ in fp32: states, old_velocities, next_states, old_means. A worked example for the two paper recipes:

covariance.py: computing $G(c)$

Recall the paper's estimator (§4.1):

\[ \overline{\operatorname{Cov}}(R,x_0\mid c)=\frac1K\sum_{i=1}^{K}(R_i-\bar R_c)\,(x_0^{(i)}-\bar x_{0,c}), \qquad G(c)=\frac{\overline{\operatorname{Cov}}}{\operatorname{rms}(\overline{\operatorname{Cov}})}, \qquad \operatorname{rms}(a)=\sqrt{\tfrac1D\textstyle\sum_j a_j^2}. \]

Here $D$ is the number of latent coordinates. The kernel computes this for all prompt groups at once with index_add_, so it is vectorized over groups and never loops in Python:

Where the code adds detail to the paper

  • The MAD pre-division and the $\varepsilon$ floor. In the default direction_mode="historical", the covariance is first divided by the reward MAD and only then RMS-normalized with a floor: $G = S/\max(\operatorname{rms}(S),\varepsilon)$ with $S = \overline{\operatorname{Cov}}/\text{MAD}$. Dividing by MAD first makes the floor independent of the reward scale: multiplying all rewards by 100 changes neither $S$ nor whether the floor binds. When $\operatorname{rms}(S) \geq 10^{-5}$ (essentially always), the result equals the paper's $\overline{\operatorname{Cov}}/\operatorname{rms}(\overline{\operatorname{Cov}})$ exactly, because the scalar MAD cancels. direction_mode="normalized_aggregate" skips MAD and normalizes in float64; in the toy experiments below both modes give bit-identical training.
  • Second normalization. art_loss RMS-normalizes the direction again (direction_normalization="rms"). If the floor ever did bind, this second normalization restores unit RMS. The final displacement is magnitude * direction / rms(direction).
  • Exact zero signal. Runners always pass zero_signal_mode="exact" for scalar ART (sd3.py L917, hunyuan.py L241). If all $K$ rewards of a prompt are bit-identical, summing them in fp32 can still round the mean away from the common value, making centered tiny but nonzero and producing a pure-noise direction after normalization. The exact mode zeroes such groups.
  • Dtype. Endpoints and rewards are cast to fp32 here even when the model runs in bf16 or fp16. FLUX with bf16 casts the directions back to bf16 before the loss (sd3.py L920–923) to reproduce a historical run.

The pairwise variant

DiffusionART-Pairwise (§4.4 and Appendix) replaces $R_i$ by labels $y_i \in \{0, \tfrac12, 1\}$ from disjoint pairs, then calls the same scalar kernel:

Mapping: pair is a seeded random partition of the group's $K$ rows into $M=K/2$ pairs; labels are $y_i$; the scalar kernel then computes $\overline{\operatorname{Cov}}(y, x_0\mid c)$, which by the paper's pairwise identity is proportional to $\sum_{j\,\text{non-tied}}(x^{\text{win}}_{0,j}-x^{\text{lose}}_{0,j})$, aggregated over all pairs of the prompt before normalization (prompt-global, not pair-local, guidance). The seed is seed + 1000003·(round + group_offset + group), private to the call, so resuming reproduces the same pairs.

One implementation detail goes beyond Algorithm 2 in the paper. The algorithm says every state of prompt $c$ gets target $v^{(0)}+G(c)$. In the code, row_guidance_magnitudes is multiplied by preference, so rows that belong to a tied pair get zero guidance. They become row_restore_anchor rows instead, which train toward $v^{(0)}$ itself (pure restoration), but only if some non-tied pair exists somewhere on any rank (any_preference_active, MAX-reduced across ranks in training/video_pairwise.py). Pairwise is wired only into the Hunyuan backend and requires VQ-only fixed-normalized scores.

art.py: frozen targets and the trust-region mask

art_loss takes the current prediction for a batch of items and everything else frozen. The first half builds the frozen target.

With the paper's recipe (loss_space="velocity_linear_sigma") only the else branch at L90–93 runs. Substitute the sign convention ($\tilde v=-v$):

\[ \texttt{target} = \tilde v^{(0)}_\theta - G = -\bigl(v^{(0)}_\theta + G(c)\bigr) = -v^{\text{ART}}_{\text{tgt}},\qquad \texttt{residual} = \texttt{target}-\tilde v_\theta = v_\theta - v^{\text{ART}}_{\text{tgt}},\qquad \lVert\texttt{residual}\rVert^2=\lVert v_\theta-v^{\text{ART}}_{\text{tgt}}\rVert^2 . \]

So unmasked = weight * mean(residual**2) (first line of the next quote) is exactly $w\,\operatorname{MSE}(v_\theta, v^{\text{ART}}_{\text{tgt}})$ with $w=t$ before masking. Mapping of the rest: v $=\tilde v_\theta(s_t)$ (graph-connected), old $=\tilde v_\theta^{(0)}(s_t)$, s $=t$, raw/direction $=G(c)$, magnitude $=1$, displacement $=G(c)$, weight $=t$. The x0 loss space is an alternative that regresses $\hat x_0 = x_t - t\tilde v$ onto $\hat x_0^{(0)} + G$; it is not used by the paper recipes.

The second half implements the mask of Equation (art_trust_mask):

Mapping, again with $\tilde v=-v$ and dt $=-h$:

  • movement = v - old $= -d(s_t)$, the drift since the rollout; desired_step = residual $= -(G-d)$. Hence alignment $=\tfrac1D\langle -d, -(G-d)\rangle = \tfrac1D\langle d, G-d\rangle$, the paper's outwardness test.
  • For the default velocity_mask_metric="scheduler_reference_metric" (identical to "q2_sde_kl"), L115–122 compute std$^2 = \nu^2\tfrac{t}{1-t}h = \sigma^2_{\text{ref}}(t)$ and coefficient $= -h(1+\nu^2/2)$, so
    \[ \texttt{energy} = \frac{h^2(1+\nu^2/2)^2\,\tfrac1D\lVert d\rVert^2}{2\,\sigma^2_{\text{ref}}(t)} = \frac{\lVert \mu(s_t,v_\theta)-\mu(s_t,v^{(0)}_\theta)\rVert^2}{2D\sigma^2_{\text{ref}}(t)} = m(s_t), \]
    the per-coordinate KL proxy. At $t=1$ (initial) the endpoint convention $\sigma_{\text{ref}}^2=\nu^2$, coefficient $-h$ is used, as in the paper's appendix. noise $=\nu=0.8$, threshold $=\delta=10^{-5}$.
  • masked $=\mathbf 1\{m\ge\delta\}\,\mathbf 1\{\langle d,G-d\rangle>0\}$, and the final weight is $t\,[1-\text{masked}]$, which is the paper's $w(s_t)$.

Details the code adds

  • The mask cannot fire on update 1. At update 1, movement is zero, so energy is zero (the trace printed $2.5\times10^{-16}$). The mask is effectively a second-update mechanism, exactly as the paper's diagnostics section says.
  • Activity and anchors. Rows with zero guidance (active false) are dropped from the loss unless flagged as restore anchors. Dropped rows stay in the denominator: the caller divides by the original item count. Video recipes set restore_zero_signal: true, so constant-reward prompts become anchors that train toward $v^{(0)}$; image recipes set it false.
  • Everything frozen is detached, including the mask (.detach() on L134–135), so the mask is a constant during backpropagation, as the appendix specifies.
  • Optional reference MSE (reference_prediction, reference_mse_beta) exists for a KL-like regularizer; paper recipes use none.

objectives.py and update.py: two disjoint updates

The kernel is connected to a model by ARTObjective, a callable that maps a list of (row, slot) items to a per-item loss vector:

Mapping: items is a set of states $s_t\in B$; state, sigma, old are read from the rollout cache; velocity = self.predict(...) is the only graph-connected tensor; dt is $-h$ for the cached step; self.row_directions[rows] broadcasts the prompt's $G(c)$ to each of its states. The two flags matter for FLUX and Hunyuan: Hunyuan reconstructs the old velocity from the cached transition mean, old = (old_mean - state)/dt, because the next state is rounded to bf16 in its sampler.

disjoint_windows(rows, S, updates=2) splits trajectories into two contiguous halves and puts all $S$ cached timesteps of a trajectory in the same window. In the paper's notation, $B_1$ and $B_2$ are disjoint sets of trajectories. How rows are ordered before the split differs by backend:

  • Tensor fixture and Hunyuan use the rows in prompt-major order. With several prompts per rank, window 1 holds the first half of the prompts and window 2 the second half. With one prompt per rank (Hunyuan on 32 GPUs), each window holds $K/2$ videos of that prompt.
  • SD3/FLUX shuffle the rows with a seeded randperm first (_art_update, quoted below), so each window holds a random half of the trajectories. The README recommends splitting within each prompt ($K/2$ per prompt per window) for better prompt coverage and states explicitly that this is "not a guarantee of every configuration's current split implementation".

Finally accumulated_step turns a window into exactly one optimizer step, however many physical microbatches it takes:

Each microbatch then does (losses.sum() * scale).backward() (L181–182) with scale = world / total; DDP averages gradients over world ranks, so the effective gradient is $\nabla \tfrac{1}{N_{\text{global}}}\sum_{s_t} w\,\operatorname{MSE}$, the paper's $\mathcal L(B;\theta)$ with $|B|$ counted over all ranks. After the backward passes it clips the gradient norm to training.grad_clip (1.0 in every recipe; not in Algorithm 1) and calls optimizer.step() (AdamW, weight decay $10^{-4}$ in paper recipes). For fp16 SD3 a GradScaler replays the same window on overflow.

Key idea

Microbatch size is a memory knob; the window is an algorithm knob. Halving training.microbatch produces bit-for-bit the same gradient (up to float summation order). Halving the window (more updates per rollout) changes the algorithm: it creates more chances for drift and restoration per rollout, which is precisely the dynamics the two-update design controls.

Two things are visible even in a toy. Flow-GRPO-Fast's loss is $\approx 0$ because at ratio 1 the PPO surrogate equals $-\bar A = 0$ for group-centered advantages; and its second update has a gradient norm of 0.0 or nearly so, because ratio_clip is $10^{-5}$ in these recipes: after one step almost every ratio has left $[1-10^{-5}, 1+10^{-5}]$ on the side where the clip zeroes the gradient. Checklist for a fair comparison

  • Start from the paper recipes in configs/paper/image/ or configs/paper/video/, which pin $P$, $K$, steps, learning rate, LoRA rank and evaluation cadence per method. The configs/examples/ files are four-update integration checks (the SD3 example even uses CFG 7, which the paper does not).
  • Compare on cost/training_gpu_hours as well as train/optimizer_step; methods differ in rollouts per optimizer step (NFT and ReFL: 1 update per rollout, the rest: 2).
  • Keep $P$, $K$ and the number of decoded samples per update fixed when the question is "which objective", and vary them only when the question is sample efficiency.
  • NFT has two recipes per benchmark: *_nft_ema (the tuned EMA schedule) and *_nft_onpolicy (old_policy: {rate: 0, maximum: 0}). The paper's stability claim is about the second.

The config system

Configs are YAML with three features: extends: (a path or list, merged left to right, child last), environment-variable references (a dollar sign followed by {NAME}, as in the paper recipes' model paths) that fail loudly when the variable is unset, and strict schemas (unknown keys and duplicate keys are rejected). Changing algorithm.name, model.name or reward.name in a child replaces that whole section, so options of the parent algorithm never leak into another algorithm (config.py L40–60). reward.weights is always replaced, never merged.

Pitfall: the 2026-10-14 microbatch fix

The README changelog records that Hunyuan paper recipes once inherited microbatch: 1 from the example for both rollout and update, instead of 8 (ReFL stays 1/1). That is why the paper recipe sets sampling.microbatch: 8 and training.microbatch: 8 explicitly (lines 13–18 above). With 8 videos and 16 steps per rank, microbatch 1 means 128 batch-1 transformer calls per rollout instead of 16 batch-8 calls, and 36 instead of 5 backward calls per window. The math is identical (the denominator is the window size), but GPU-hours, the paper's main metric, are not. Use a checkout that contains commit 0fb23a7 or later.

Experiments to build intuition

The fixture cannot change algorithm options (its validator rejects them), so I drove the repo's kernels directly with the fixture's MLP and reward: $P=4$, $K=4$, 6 steps, lr $3\times10^{-3}$, 40 rollouts, 5 seeds, evaluated on fixed noise. These numbers are a toy; they show mechanics, not the paper's results.

Below, each experiment lists the change for real runs, what the paper reports, and what the toy shows.

  1. Turn off the second update. Image: add algorithm.options.updates_per_rollout: 1; the paper ships configs/paper/image/sd3_ocr_art_one_update.yaml. Paper (§5.1, T2I ablation figure): "ART: 1 update" learns quickly but gradually deteriorates, while the second update adds restoration and long-term stability. So expect similar early curves and a late decline without the second update; read train/reward over the full 1000 updates and train/grad_norm/before_clip. Toy: $-1.03$ vs $-0.90$ after 40 rollouts, but this short horizon cannot show the late deterioration, and one update per rollout also means half the optimizer steps for the same rollouts. Compare at equal rollouts and at equal optimizer steps.
  2. Vary $K \in \{2,4,8\}$. Video: hunyuan_pairwise_vq_k{2,4,8}.yaml (pairwise) and hunyuan_scalar_vq_k8.yaml. Paper: pairwise $K=2$ reaches final VQ 12.235 versus 12.092 for $K=8$ with 3.4× fewer GPU-hours. Toy: $K=8$ is best per rollout, but it also uses twice the samples of $K=4$. The fair toy comparison is P4K4 versus P8K2 at 16 samples each: $-0.90$ vs $-0.86$, i.e. more prompts with smaller groups is at least as good, matching the README's advice on prompt diversity.
  3. Scalar vs pairwise. Video: add pairwise: {seed: 42} (requires VQ-only fixed-normalized reward). Paper: pairwise is close to scalar under the scalar evaluation metric. Toy: at $K=2$ pairwise and scalar are bit-identical ($-0.9960$ both), because with two samples the centered label vector $(\pm\tfrac12)$ has the same sign pattern as the centered rewards, and normalization removes the magnitude (Exercise 5.5). At $K=4$ pairwise discards within-pair magnitude and cross-pair information and is slightly worse.
  4. ART vs NFT on-policy without EMA. Image: sd3_pickscore_art.yaml vs sd3_pickscore_nft_onpolicy.yaml (same $P$, $K$, steps, lr). Paper (§3 and T2I results): DiffusionNFT (on-policy) collapses on SD3.5-M while ART does not, because the self-consistency force is no longer restrained by an EMA. Read train/reward and train/grad_norm/before_clip together; a collapse shows as a reward drop after an early rise. Not run here.
  5. Change the guidance normalization. Set covariance.scale_mode: raw_covariance (step size proportional to the raw covariance RMS) or direction_mode: normalized_aggregate. Paper: RMS normalization "fixes the guidance magnitude across prompts and reward models". Toy: normalized_aggregate is identical to the default (the MAD cancels), and raw_covariance is slower ($-0.97$ vs $-0.90$) because low-spread prompts get tiny targets. With a real reward on a different scale (PickScore raw logits around 20 vs fixed-normalized around 0.8) the raw mode would also change the effective learning rate, which is exactly what unit normalization prevents.
  6. Turn off the trust-region mask. loss.corrective_mask_enabled: false. Paper (Appendix on masking): on images the no-mask run is as good or slightly faster; on HunyuanVideo it shows larger late-stage gradient and drift spikes (max first-update grad norm 3.33 vs 1.96). Toy: slightly better without the mask ($-0.88$ vs $-0.90$), with mean drift $2.05\times10^{-5}$ vs $1.90\times10^{-5}$, consistent with the image finding. Watch train/grad_norm/before_clip on odd steps when you try this on video.

Porting notes for an LLM RL framework

If you maintain a Megatron + SGLang style stack, this is what a diffusion integration needs, in order of surprise.

  • Rollout engine. Generation is a fixed-length loop of $T$ full-sequence transformer calls on a latent tensor, with no KV cache and no sampling. The engine must return, per sample, the selected intermediate states and predicted velocities, not just the final output. Batching is trivial (all samples have the same shape); CFG, if used, doubles the batch.
  • Data plane. You ship latents, not token ids: about 1.4 GiB of fp32 cache per SD3 rank, 0.9 GiB per Hunyuan rank (worked out above). If the rollout engine and trainer are disaggregated, plan for tensor transport (NCCL or RDMA, pinned buffers), not JSON. Only states and old_velocities are needed for ART, so you can halve the repo's footprint; bf16 storage halves it again at some fidelity risk.
  • No logprobs, but you still need parity. ART needs no transition likelihood, so the classic rollout/training logprob mismatch disappears. It is replaced by a velocity mismatch: if the engine's $v^{(0)}$ differs from the trainer's forward at $\theta_{\text{old}}$, update 1 already sees a spurious drift $d\neq0$, which biases the target and can trip the mask. Either make the forwards bitwise aligned, or recompute $v^{(0)}$ in the trainer (one extra no-grad forward per item, which is what ART was designed to avoid).
  • Reward services. Rewards need a VAE decode, then a scorer (PickScore, a VLM-based VideoReward, OCR or detector workers). These look like generative reward models in LLM RL: GPU-heavy, best run as separate services with their own batching. The repo encodes videos to MP4 before scoring, so the codec is part of the reward.
  • Group placement. Guidance needs all $K$ endpoints of a prompt in one place. The repo keeps each prompt's group on one data-parallel rank and computes $G(c)$ locally; this is cheaper than gathering endpoint tensors across ranks, and it is the analogue of computing GRPO group advantages, except the statistic is a $D$-dimensional vector.
  • Loss and steps. Per-item MSE with a fixed denominator, two optimizer steps per rollout over disjoint trajectory halves, global grad clip. In a Megatron trainer this is a custom loss function plus "two minibatches per rollout"; data and pipeline parallelism need nothing special. The covariance and target can be precomputed on the rollout side and shipped as a per-sample target, so the trainer only sees (state, $t$, condition, target, weight).
  • Old-policy shadows. ART needs no old-policy weights at all. NFT baselines do: training/fsdp_shadow.py keeps a CPU copy of each rank's FSDP local shards and swaps them in for old-policy forwards, without ever materializing a second full model on GPU. The Megatron equivalent is a CPU copy of the local TP/PP shards.
  • Weight sync. After both updates, push weights to the rollout engine as usual; with LoRA (image recipes) only the adapters change.

Pitfalls collected

Pitfall: computing guidance on a microbatch

The covariance must use the complete group of $K$ endpoints. art_scalar_covariance's docstring says "Complete-group covariance, never a microbatch estimator", and the distributed runners keep groups rank-local. If you shard a group across ranks or compute $G$ per update window, you get a noisier and differently normalized direction, and the two windows no longer share one frozen target.

Pitfall: examples are not recipes

configs/examples/*.yaml are four-update integration checks with deliberately small $P$, $K$ and sometimes different sampling (CFG 7 in the SD3 example, microbatch 1 in Hunyuan). Comparisons belong in configs/paper/, and even those are labeled as candidates, not certified reproductions (see each file's provenance block).

Pitfall: world size and P

sampling.prompts_per_rollout is global and must be divisible by the number of workers (train.py L114–117). Doubling GPUs with the same $P$ halves the per-rank groups, which changes how the two windows are composed in prompt-major backends but not the guidance itself.

Exercises

Exercise 5.1 — Find every place where $K$ enters the guidance computation. Does the magnitude of $G(c)$ depend on $K$?

In art_scalar_covariance, $K$ is counts (L66). It enters at three places: the group means (L69, L70), the MAD (L80, divided by counts) and the covariance denominator (L82, counts - 1 for the unbiased reduction). The direction is signal / signal_rms (L103) with signal = covariance / mad: any positive scalar that multiplies the covariance or the MAD cancels in this ratio, so both $1/(K-1)$ and the $1/K$ inside MAD disappear. The magnitude is the constant 1 for unit_normalized_covariance (L90), and art_loss normalizes again. So $\operatorname{rms}(G(c))=1$ for every $K\ge2$ whenever the group is active; $K$ affects only the estimator's noise (which direction you get). Outside the kernel, $K$ also enters disjoint_windows (rows $=PK$ must split evenly), the loss denominator (items per window $= PK S/2$) and, for pairwise, the pair partition (group_size, which must be 2, 4 or 8). With scale_mode: raw_covariance, the magnitude becomes rms, which does depend on $K$ through $1/(K-1)$.

Exercise 5.2 — Modify the CPU smoke config to run Flow-GRPO-Fast. Why is the second update's gradient almost zero?

Create a child config next to the example (paths in extends are relative to the child file) and run it:

extends: cpu_smoke.yaml
name: cpu-smoke-fast
algorithm: flow_grpo_fast
runtime:
  output_dir: outputs/cpu-smoke-fast
uv run --locked visual-rl --config configs/examples/cpu_smoke_fast.yaml

Because the algorithm name differs from the parent's, the whole algorithm section is replaced (no ART options leak in). The fixture then samples with one Flow-SDE step at index 0 and ODE elsewhere (tensor_fixture.py L163–165), computes advantages with group_advantages(mode="global_population_std", eps=1e-4), and uses clipped_grpo_loss with ratio_clip=1e-5 (L196–211). The real run above logged gradient norms 0.309, 0.0, 0.226, 0.0023. At update 1 all ratios are exactly 1 and the gradient is $-\nabla\tfrac1N\sum A_i\rho_i$. After one AdamW step, almost every ratio has moved by more than $10^{-5}$. The PPO surrogate $\max(-A\rho, -A\operatorname{clip}(\rho))$ has zero gradient whenever $\rho$ moved past the clip boundary in the advantage's favorable direction, which is what the first update just did. So the second window is almost entirely clipped. This is the LLM-RL intuition carried over unchanged, and it shows how conservative $10^{-5}$ is; the paper's credit-assignment argument is that this clipped, per-transition signal is a slow way to move a continuous policy.

Exercise 5.3 — All $K$ rewards of every prompt are equal. Trace what happens to guidance, loss and the optimizer in an image run and in a video run.

Kernel. Runners pass zero_signal_mode="exact". In art_scalar_covariance, maxima == minima marks the group constant (L73–75), so centered is forced to exactly 0 (L77). Then mad is 0 and covariance is 0, so active is false (L94), magnitudes become 0 (L96) and directions become 0 (L108). Without exact mode, the fp32 mean of identical values could differ from them by one ulp, giving a nonzero centered whose normalized direction would be pure rounding noise; exact mode exists to prevent that.

Loss. In art_loss, active is false for every item (L127). Unless an item is a restore anchor, keep is false and its per_item_loss is 0 (L135–136), while it still counts in the denominator.

Image runner. Image recipes use restore_zero_signal: false, so no anchors. ARTObjective.has_guidance is false; sd3.py (L837–845) logs system/skipped_zero_guidance: 1 with the rewards, does not step the optimizer, does not advance train/optimizer_step, and samples a new rollout. Under DDP the flag is MAX-reduced, so a rank with no signal still runs both windows when another rank has signal (image_ddp.py L357–358). NoSignalGuard warns at exponentially spaced counts and, if runtime.max_consecutive_no_signal_rollouts is set (default: unset, no limit), stops training after that many consecutive skips.

Video runner. Hunyuan recipes use restore_zero_signal: true, so the inactive rows become anchors (hunyuan.py L242). For an anchor the displacement is 0, so the target is the old velocity and the loss is $t\,\operatorname{MSE}(v_\theta, v^{(0)})$. On update 1 this is 0 with zero gradient; on update 2 it pulls the drift caused by update 1 back toward $v^{(0)}$: pure restoration, no guidance. The windows are executed (anchor-only rollouts are not skipped).

Mixed case. If only some prompts are constant, the active prompts train normally and the constant ones contribute zeros that still dilute the mean, so train/loss on update 1 equals mean $t$ times the active fraction. That is a way to read the fraction of saturated prompts off the loss curve.

Exercise 5.4 — Add train/art/masked_fraction and a drift metric to metrics.jsonl.

art_loss already computes the values; ARTObjective.__call__ discards them. Keep a list on the objective and reduce it after each window. The smallest change to training/objectives.py:

@dataclass
class ARTObjective:
    ...
    reconstruct_old_from_mean: bool = False
    diagnostics: list = field(default_factory=list)          # new

    def __call__(self, items):
        ...
        terms = art_loss(...)                                # unchanged
        self.diagnostics.append({k: terms[k].detach().cpu()  # new
                                 for k in ("masked", "movement_score")})
        return terms["per_item_loss"]

    def pop_metrics(self):                                   # new
        masked = torch.cat([d["masked"] for d in self.diagnostics]).float()
        score = torch.cat([d["movement_score"] for d in self.diagnostics])
        self.diagnostics.clear()
        return {"train/art/masked_fraction": masked.mean().item(),
                "train/art/movement_score_mean": score.mean().item()}

Then in the runner, after each accumulated_step for ART, call metrics.update(objective.pop_metrics()) before writing the line. Under DDP or FSDP, all-reduce the sums and counts before dividing, otherwise each rank logs its local fraction and only rank 0's is exported. I tested the same logic as a subclass outside the repo on the smoke iteration:

@@F /Users/hejian.sang/Downloads/DiffusionART-paper/tutorial/scratch/step5/out/ex_logging.txt@@

As expected, update 1 shows zero drift and no mask; update 2 shows mean drift energy $3.5\times10^{-6}$ (below $\delta$ on average) with 1 of 12 items masked. The paper's "velocity drift before second updates" curve is the update-2 value of this metric.

Exercise 5.5 — Show that DiffusionART-Pairwise with $K=2$ produces exactly the scalar guidance (when the pair is not tied), and explain the toy result where both gave $-0.9960$.

For one prompt with endpoints $x^{(1)}, x^{(2)}$ and rewards $R_1 > R_2$, the scalar covariance with the code's unbiased reduction is $\tfrac{1}{1}\bigl[(R_1-\bar R)x^{(1)} + (R_2-\bar R)x^{(2)}\bigr] = \tfrac{R_1-R_2}{2}(x^{(1)}-x^{(2)})$. Pairwise labels are $y_1=1, y_2=0$, giving $\tfrac12(x^{(1)}-x^{(2)})$. Both are positive multiples of $x^{(1)}-x^{(2)}$, so after RMS normalization they are identical: the winner-minus-loser direction, as the paper's appendix states. With $K=2$ there is exactly one pair, so preference is true for both rows whenever $R_1\ne R_2$, and row_guidance_magnitudes equals the scalar magnitude 1. The only differences are a tie (scalar: exact zero signal; pairwise: anchors if some other prompt has a preference) and the pair-seeding RNG, which consumes no global RNG state. Hence the two toy runs performed the same arithmetic on the same random stream and printed the same $-0.9960 \pm 0.0724$. For $K\ge4$ the two differ: pairwise uses only within-pair order, so a sample that wins its pair narrowly counts as much as one that wins by a lot, and cross-pair differences are ignored.

Takeaways

  • The algorithm lives in three pure kernels: art_scalar_covariance/art_pairwise_covariance ($G(c)$), art_loss (target, $t$-weighting, mask) and disjoint_windows + accumulated_step (two optimizer steps with a fixed denominator). Backends choose the model; algorithm.name chooses the branch.
  • The code's velocity is $\tilde v = \epsilon - x_0 = -v$ and dt is negative. With that substitution, target = old - G is the paper's $v^{(0)}+G$, and the mask's energy and alignment are exactly $m(s_t)$ and $\langle d, G-d\rangle$.
  • The code adds an unbiased $K-1$ denominator, a MAD pre-division with a $10^{-5}$ floor, a second RMS normalization, exact zero-signal gating, restore anchors for video and tied pairs, grad clip 1.0, and fp32 statistics. None of these change the paper's math in the normal regime.
  • Update 1's loss equals the mean trained $t$ times the active fraction; this is a free health check. The mask can only fire on update 2.
  • The rollout cache (states and old velocities, fp32, on CPU) is the price of skipping NFT's extra old-policy forward: about 1.4 GiB per SD3 rank, 0.9 GiB per Hunyuan rank.
  • Microbatch sizes are memory knobs; the window count is an algorithm knob. Drift and mask fraction are not logged by default.
